# Homegate investigation (2026-05-18)

## Context

The original `@wabe/source-homegate` plugin in this slice was modeled on the
MIT-licensed [denysvitali/homegate-rs](https://github.com/denysvitali/homegate-rs)
reference implementation, which uses HTTP Basic auth plus an HMAC-derived
`X-App-Id` header against `api.homegate.ch`. That reference implementation is
now stale: requests built against it return HTTP 403. A mitmproxy capture of the
current iOS Homegate app (version 15.62.0 on iOS 26.4.2) confirmed both the
auth model and the public-search endpoint have changed materially, and that the
public-search path is now fronted by anti-bot infrastructure. This document
preserves the findings so the eventual re-investigation spec can pick up
without re-running the capture.

## Current auth model (Auth0 + Google SSO)

User-bound endpoints (favourites, saved searches, etc.) are now gated by Auth0
OAuth2 bearer tokens. Login is via Google SSO — no headless-friendly path
without user interaction.

- Issuer: `https://auth.homegate.ch/`
- Underlying tenant: `smg-re-hg-prod.eu.auth0.com`
- Client ID (iOS app, Auth0 `azp`): `lU7SBprOA383MV4TCsRfP9wUPc4JAcy1`
- Scopes used: `openid profile email offline_access`
- Token lifetime: 1800 s (30 min)
- Refresh-token rotation: ENABLED — each refresh consumes the old refresh
  token and returns a new one.
- Refresh token endpoint: `POST https://auth.homegate.ch/oauth/token`
  with `Content-Type: application/json` and body:

  ```json
  {
    "scope": "openid profile email offline_access",
    "grant_type": "refresh_token",
    "client_id": "lU7SBprOA383MV4TCsRfP9wUPc4JAcy1",
    "refresh_token": "<redacted>"
  }
  ```

- Login flow: Google SSO, observed `sub: google-oauth2|...`. Not
  headless-friendly without user interaction.

## Search endpoint

`POST https://api.homegate.ch/search/listings`

**No `Authorization` header required on search** — auth gates user-bound
endpoints (favourites, etc.) only. The binding constraint for search is the
anti-bot stack, not Auth0.

Required headers observed:

- `Content-Type: application/json`
- `X-App-Id: <26-digit decimal nonce>` — derivation unknown; not the
  homegate-rs HOTP HMAC. Assume per-request generated by the iOS app.
- `X-UDID: <iOS-style UUID>`
- `X-App-Version: Homegate/15.62.0/iPhone/iOS/23`
- `User-Agent: ch.homegate.Homegate/15.62.0 (iPhone, iOS 26.4.2, Scale 3.00)`

Required cookies (issued by anti-bot challenge, not by login):

- `datadome=<redacted>` — DataDome session cookie
- `__cf_bm=<redacted>` — Cloudflare bot management

Response header confirms protection: `x-datadome: protected`.

Request body schema (NEW shape, completely different from homegate-rs):

```json
{
  "sortDirection": "desc",
  "query": {
    "offerType": "RENT",
    "propertyType": "APARTMENT_OR_HOUSE",
    "monthlyRent": { "to": 4500 },
    "numberOfRooms": { "from": 4.5 },
    "livingSpace": { "from": 80 },
    "location": {
      "geoTags": ["geo-zipcode-8008", "geo-zipcode-8032", "geo-zipcode-8053"]
    }
  },
  "from": 0,
  "size": 24,
  "sortBy": "listingType",
  "trackTotalHits": true
}
```

Response shape: `{ from, size, total, results, maxFrom }`. Use `size: 0`
for a count-only probe; real fetch uses non-zero size.

Location filter uses `geo-zipcode-NNNN` geo-tags, not lat/lon radius. Tag
vocabulary likely also includes `geo-city-zurich`, `geo-canton-zh`, etc. — to
be determined.

## Listing detail endpoint

`GET https://api.homegate.ch/listings/listings?ids=<id1>,<id2>,...&fieldset=srp-list`

- Batch fetch by id (CSV in query)
- `fieldset=srp-list` for list-view subset; other fieldsets likely exist
  (e.g. `pdp-full` for the detail page).
- Auth observed: optional Bearer (sent by the app when the user is logged in,
  but probably not required for public listings).

## Anti-bot stack

- **DataDome** — the binding constraint for Node clients.
- **Cloudflare Bot Management** (`__cf_bm` issued via standard CF challenge).
- **TLS fingerprint** (JA3/JA4) likely also evaluated.
- The iOS app does NOT pin TLS — verified that mitmproxy CA installation
  suffices on iOS 26.4.x with Homegate 15.62.0. This is likely to change in
  future iOS app releases.

## Implementation path for a future `@wabe/source-homegate` v2 spec

Recommendation, not commitment.

- **Option A**: stealth headless browser (Playwright + `playwright-extra` +
  stealth + residential proxy). High fragility, ongoing maintenance against
  DataDome rule updates, IP-rotation cost.
- **Option B**: reverse-engineer the iOS `X-App-Id` algorithm plus a DataDome
  challenge solver. High upfront cost, brittle against version updates.
- **Option C**: use an Apify actor or a paid DataDome-bypass service.
  Conflicts with the self-hosted / AGPL ethos, adds an external dependency.
- **Option D**: drop Homegate entirely and prioritize other portals. Flatfox
  public API plus a future email-alert ingestion path is already two coverage
  channels; the marginal coverage gain from Homegate may not be worth the
  maintenance burden.
